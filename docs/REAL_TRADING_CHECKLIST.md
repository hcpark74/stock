# 실전투자 전환 점검표

최종 코드 점검일: 2026-07-23

이 문서는 PAPER에서 정상 동작했다는 사실만으로 REAL을 활성화하지 않도록 코드 수준의 차이와 승인 조건을 기록한다. 아래 `REAL-BLOCKER`가 하나라도 남아 있으면 `KIS_MODE=REAL`로 전환하지 않는다.

## 이번 점검에서 완료된 항목

- KIS REST 지연 측정에서 로컬 호출 제한 대기와 실제 HTTP 응답 시간을 분리했다.
- 청산 시 `trades.exit_qty`, 수수료·세금 제외 `pnl_amount`, 청산 직전 `high_price`를 하나의 DB UPDATE로 저장한다.
- 기존 CLOSED 거래의 비어 있는 `exit_qty`와 `pnl_amount`는 저장된 매도 체결 주문으로 기동 시 보완한다.
- 이미 DB에 더 높은 `high_price`가 있으면 청산 시 낮은 값으로 덮어쓰지 않는다.
- 시장가 주문의 제출가(`order_price=0`), 판단 기준가(`trigger_price`), 체결가(`fill_price`)를 분리한다.
- F3/F4/F5의 확인된 체결은 주문 호출 직전부터 체결 조회 확인까지의 `fill_latency_ms`를 기록한다. 체결 미확인 F4 경로는 R1 해결 전까지 NULL로 남긴다.

## REAL-BLOCKER

### R1. F4 전량 체결 확인과 부분체결 처리가 필요

현재 `src/modules/f4_tracking.py::_poll_fill`은 누적 체결수량이 1주 이상이면 반환한다. 주문수량 전부가 체결됐는지 검증하지 않으며, 조회 시간 초과로 `None`이 반환돼도 호출부는 트리거 가격을 체결가처럼 사용해 거래를 닫을 수 있다.

REAL 전환 전 다음을 구현한다.

- 매도 주문을 전송한 직후 `orders`에 `PENDING`으로 먼저 기록한다.
- 주문수량과 누적 체결수량을 비교해 `PARTIAL_FILL`과 `FILLED`를 구분한다.
- 미체결 잔량의 취소 확인 전에는 재주문하지 않는다.
- 체결 조회가 불명확하면 거래와 상태를 닫지 않고 `EXITING_UNCONFIRMED`로 격리한다.
- 잔고, 주문 상태, 체결 내역의 세 자료가 일치할 때만 CLOSED로 확정한다.

### R2. HOLDING과 CLOSED 사이에 영속적인 EXITING 상태가 필요

F5는 중복 매도를 막기 위해 실제 매도 전에 상태를 `CLOSED`로 변경한다. 이후 주문이나 체결 확인이 실패하면 계좌에는 주식이 남아 있지만 로컬 상태는 CLOSED일 수 있다.

REAL 전환 전 `EXITING` 상태를 추가하고 다음 전이를 보장한다.

```text
HOLDING -> EXITING -> CLOSED
                 \-> EXITING_UNCONFIRMED
```

- `EXITING` 진입 시 주문번호, 주문수량, 누적 체결수량을 상태 파일과 DB에 저장한다.
- 재시작 시 신규 매도보다 기존 주문·잔고 대사를 먼저 수행한다.
- CLOSED는 잔고 0과 체결수량 일치가 확인된 뒤에만 기록한다.

### R3. F4 주문 응답 유실 시 재시작·재주문 대사가 필요

POST 응답이 유실되면 주문 접수 여부가 불명확하다. 현재 F4는 이 상태를 영속적으로 복구할 주문 상태가 없다. 주문 전송 시 클라이언트 상관 ID 또는 주문 시각·종목·수량을 저장하고, KIS 주문 조회로 기존 주문을 찾은 뒤에만 추가 주문 여부를 결정해야 한다.

### R4. 피라미딩을 다시 활성화하려면 평균단가·수량 집계를 수정해야 함

현재 `FIRST_RATIO=1.00`이라 2차 매수는 비활성이다. 이를 낮추면 상태의 수량은 늘지만 `trades.entry_price`와 `entry_qty`가 체결 가중평균과 총수량으로 갱신되지 않아 손익이 틀릴 수 있다. 해당 집계와 재시작 복구 테스트가 완성될 때까지 `FIRST_RATIO=1.00`을 유지한다.

## 실전 전 권장 보완

- 이론적 스탑과 KRX 호가단위로 보정한 실행 트리거 가격을 구분해 기록한다.
- F1 종료 시 예상체결가 조회의 실제 네트워크 지연 `p50/p95/max`, 표본 수, 실패·호출 제한 건수를 요약 로그로 남긴다.
- `pnl_amount`는 현재 수수료·세금 제외 값이다. 계좌 실현손익과 대사하려면 비용 컬럼을 별도로 저장한다.
- 실전 TR ID, 응답 필드명, 취소가능수량 조회, 휴장일 조회를 최소 수량 주문으로 검증한다.
- `RATE_LIMIT_HIT`, 토큰 갱신, WebSocket 단절, REST 백업 전환을 장 시작 전 실전 서버에서 확인한다.
- 프로세스·네트워크 장애 시 MTS/HTS로 즉시 수동 청산할 운영자를 09:00~11:00 동안 확보한다.

## 설정 확인

- `DRY_RUN=0`
- `KIS_MODE=REAL`
- 실전 REST/WebSocket URL과 실전 키·계좌번호 사용
- `F2_RETRY_F1_ON_FAIL=0`
- 초기에는 `F3_ALLOC_RATIO`를 낮춰 최소 위험금액으로 시작
- Telegram CRIT 알림 실수신 확인
- `FIRST_RATIO=1.00` 유지

## REAL 승인 기준

다음 조건을 모두 만족해야 한다.

1. R1~R4가 코드와 자동 테스트에서 해결됐다.
2. PAPER에서 부분체결, 체결조회 실패, 주문응답 유실, 재시작 시나리오가 통과했다.
3. 실전 서버 최소 수량 스모크 테스트에서 주문·취소·체결·잔고·DB가 일치한다.
4. 청산 후 `trades.exit_qty`가 매도 체결 합계와 같고, `pnl_amount`가 수수료 제외 계산과 일치한다.
5. 운영자가 장애 대응 및 수동 청산 절차를 실제로 수행해 봤다.
